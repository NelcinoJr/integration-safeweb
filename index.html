Definição do Projeto

Conectar o app ContaÁgil (PHP CodeIgniter + jQuery) ao PSC SafeWeb / SafeID, permitindo ao cliente autorizar certificados na nuvem, armazenar tokens com segurança e utilizar a API PSC para assinaturas. O projeto cobre os dois modelos de integração (QRCode e Aplicação Confiável/CA) e os tipos de assinatura previstos (RAW/CMS, ICP, PAdES com carimbo), com validação via Postman restrita ao escopo fechado desta entrega de 15 du.

Funcionalidades do Produto (User Experience)

Conexão e Gestão

  • Multi-fluxo: QRCode (OAuth + PKCE) ou CA (Senha + Identificador).
  • Dashboard de Status: Monitoramento de conexão (Ativo, Expirado, Revogado) via jQuery no portal do cliente.
  • Consultas Integradas: Certificate-info e Discovery direto no app.

Assinatura e Validação

  • Motores PSC: Assinatura de Hash (RAW/CMS) e ICP (AD-RB / AD-RT).
  • Pipeline PAdES: Fluxo completo (Start, Apply, Finish) com suporte a carimbo.
  • Verify: Validação server-side de arquivos/assinaturas via Client Token.

Visão do Projeto: Transformação da Assinatura Digital

Alinhamento estratégico: O impacto da transição do modelo de vouchers externos para a integração PSC nativa.

Cenário Atual (Voucher + Soluti)

Fluxo Principal:

  1. Usuário solicita um voucher no ContaÁgil.
  2. Sistema gera código estilo cupom (Ex: QDAS123123ASD).
  3. Usuário leva documentos ao fluxo externo na Soluti.
  4. Informa o voucher na Soluti para validar o serviço/certificado.
  5. Retorna ao ContaÁgil para finalizar o processo.

Dores do Modelo:

  • • Jornada Descontínua: App → Canal Externo → Retorno.
  • • Rastreabilidade: Difícil conciliar eventos Soluti vs Voucher.
  • • Automação Baixa: Validação manual e dependência de A1/A3 locais.
  • • Custo de Suporte: Alto volume para localizar etapa do usuário.

Resultado: Processo lento, dependente de hardware e canais externos, com auditoria limitada.

Com Integração SafeID/PSC (Estado Desejado)

QRCode (OAuth + PKCE)
Autorização via celular gera token de usuário instantâneo. Fim da dependência de drivers e certificados na máquina.

CA (Aplicação Confiável)
Fluxo authorize-ca para uso recorrente pesado. Assinatura fluida e automatizada para o dia a dia.

Ganhos em relação ao Voucher:

  • • Orquestração Nativa: Assinatura disparada e controlada 100% dentro do app.
  • • Pipeline PAdES: Automatização total de carimbos e informações visuais no PDF.
  • • Verify Server-Side: Trava de segurança Valid / Invalid automática em cada documento.
  • • Conformidade: Base ICP-Brasil integrada com trilha de auditoria completa.

"Deixa de ser um código externo e passa a ser assinatura e checagem integradas ao ecossistema ContaÁgil."

§6DDL (Guia Oficial)

Nota de Validação Técnica: Toda e qualquer coluna e restrição abaixo deve ser cruzada com o ambiente real de mysql-dev da ContaÁgil antes da consolidação do script final em ambiente de staging.
CREATE TABLE IF NOT EXISTS PscOAuthSessions (
  id INT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  state VARCHAR(128) NOT NULL,
  code_challenge VARCHAR(255) NOT NULL,
  code_verifier TEXT NOT NULL,
  CodEmpresa INT NOT NULL,
  CodCliente INT NOT NULL,
  scope VARCHAR(64) NOT NULL DEFAULT 'signature_session',
  redirect_return_url VARCHAR(512) DEFAULT NULL,
  login_hint VARCHAR(20) DEFAULT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  consumed_at TIMESTAMP NULL DEFAULT NULL,
  ip_address VARCHAR(45) DEFAULT NULL,
  user_agent VARCHAR(512) DEFAULT NULL,
  UNIQUE KEY uk_psc_oauth_state (state),
  KEY idx_psc_oauth_created (created_at),
  KEY idx_psc_oauth_empresa (CodEmpresa)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE IF NOT EXISTS PscAccessTokens (
  id INT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  CodEmpresa INT NOT NULL,
  CodCertificado INT DEFAULT NULL,
  scope VARCHAR(64) DEFAULT NULL,
  access_token_enc TEXT NOT NULL,
  expires_at DATETIME NOT NULL,
  authorized_identification_type VARCHAR(8) DEFAULT NULL,
  authorized_identification VARCHAR(20) DEFAULT NULL,
  slot_alias VARCHAR(255) DEFAULT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  revoked_at TIMESTAMP NULL DEFAULT NULL,
  KEY idx_psc_token_empresa (CodEmpresa),
  KEY idx_psc_token_expires (expires_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE IF NOT EXISTS PscApiAudit (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  correlation_id CHAR(36) NOT NULL,
  CodEmpresa INT DEFAULT NULL,
  endpoint VARCHAR(255) NOT NULL,
  http_status SMALLINT DEFAULT NULL,
  duration_ms INT DEFAULT NULL,
  error_code VARCHAR(64) DEFAULT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  KEY idx_psc_audit_corr (correlation_id),
  KEY idx_psc_audit_empresa (CodEmpresa)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

§7OAuth + PKCE

  1. Persistir localmente em sessão de banco o state mapeado com o verifier e o challenge gerado via SHA-256.
  2. Redirecionar o navegador do usuário ao fluxo do PSC.
  3. Tratamento obrigatório do retorno do Callback: abortar transação imediatamente em cenários de rejeição pelo usuário (user_denied).
  4. Efetuar requisição server-side `POST /oauth/token`; submeter o payload do token à cifragem criptográfica antes de persistir o registro no banco.

§9eNotas / Convivência A1

Garantia operacional restrita à coexistência paralela de processos até o término da validação técnica em ambiente isolado. É mandatório isolar escopos para mitigar impactos inesperados na rotina de faturamento ativo da plataforma.

§10Mapeamento de Cobertura do Postman

A suíte de testes deve cobrir obrigatoriamente a totalidade dos endpoints expostos e operados no ciclo de 15 du:

  • GET /oauth/authorize (Handshake, PKCE, validação de state)
  • POST /oauth/token (Emissão de credencial de assinante via autorização externa)
  • POST /oauth/authorize-ca (Autenticação baseada em Aplicação Confiável)
  • POST /oauth/pwd_authorize (Handshake baseado em credencial estática e PIN)
  • POST /oauth/signature (Assinatura base binária / Hashes estruturais RAW/CMS)
  • POST /oauth/signature-icp (Assinatura digital padrão ICP-Brasil)
  • POST /oauth/pades-signature/start (Abertura e registro do pipeline de documento PDF)
  • POST /oauth/pades-signature/apply (Estampagem do carimbo visual e hash no PDF)
  • GET /oauth/pades-signature/finish (Consolidação de escrita e fechamento do arquivo PDF)
  • GET /oauth/pades-signature/info (Inspeção estrutural de integridade de assinatura em PDF)
  • GET /oauth/certificate-info (Recuperação de metadados do par de chaves públicas)
  • GET /oauth/certificate-discovery (Varredura e localização de PEMs e cadeias)
  • POST /oauth/user-discovery (Checagem cadastral prévia do assinante por documento)
  • POST /oauth/client_token (Autenticação do servidor ContaÁgil perante o ecossistema PSC)
  • POST /oauth/signature_verify (Motor validador server-side de hashes e integridade)

F2 — Barramento HTTP, Cifragem Segura e Fluxos Autenticadores (5,0 du)

SAFE-104 · Configuração de Escopo de Ambientes (ENV) e Fail-Fast Security Guard · 0,5 du

Configurar o isolamento das variáveis do bloco §5 no arquivo env-settings/getenv. Implementar uma validação rígida de boot para que a aplicação lance uma exceção e falhe imediatamente caso constantes essenciais como PSC_TOKEN_ENCRYPTION_KEY estejam ausentes no ambiente de Staging.

SAFE-105 · Wrapper Cliente HTTP PSC & Sanitização Estrita de Logs · 1,5 du

Criar a classe PscSafeWebClient para centralizar as requisições GET/POST JSON e POST Form x-www-form-urlencoded usando cURL ou Guzzle existente. Mapear retornos HTTP status para exceções específicas do domínio e garantir mascaramento estrito em funções de depuração para nunca imprimir ou vazar tokens em claro nos logs.

SAFE-106 · Camada de Cifragem Criptográfica Simétrica (AES-256-GCM) · 0,5 du

Desenvolver métodos no Service para cifragem simétrica de tokens em repouso antes do INSERT na PscAccessTokens. O formato de armazenamento deve ser base64(iv+ciphertext+tag). Adicionar teste de negação lançando exceção controlada se o token gravado for intencionalmente adulterado ou a chave GCM for inválida.

SAFE-107 · Engine de Handshake e Fluxo OAuth Inicial via PKCE · 1,5 du

Implementar no Service o método iniciarOAuthPKCE. Gerar code_verifier, code_challenge em S256 e state randômico. Persistir esses hashes temporários na tabela PscOAuthSessions vinculando a empresa e retornar a montagem exata da URL de redirect para o endpoint /oauth/authorize do PSC SafeWeb.

SAFE-108 · Implementação do Canal de Aplicação Confiável (CA) · 1,0 du

Desenvolver método autenticarAplicacaoConfiavel no Service. Consumir os endpoints /oauth/client_token e /oauth/authorize-ca. Processar o payload gerado a partir do identificador e da senha criptografada em vault, persistindo o token de repouso sob as mesmas regras AES-256-GCM do fluxo clássico.

F3 — Motores de Assinatura, Pipelines e Motor Validador (4,5 du)

SAFE-109 · Motor de Assinatura Core: Hashes Brutos (RAW/CMS) e ICP-Brasil · 1,5 du

Construir no Service a lógica de processamento de assinaturas digitais. Implementar os métodos assinarHashBruto (/oauth/signature) e assinarDiretrizIcp (/oauth/signature-icp). Garantir o correto envio do alias do certificado em nuvem e a extração do payload de assinatura retornado, adicionando registro à tabela PscApiAudit.

SAFE-110 · Pipeline Orquestrador de Assinatura Documental PAdES (PDF) · 2,0 du

Desenvolver a máquina de estados para assinaturas em lotes e arquivos PDF no padrão PAdES. Implementar de forma linear e atômica o ciclo de chamadas tripartido da API SafeWeb: /pades-signature/start (registro de fluxo), /pades-signature/apply (aplicação do carimbo visual com metadados estruturais) e /pades-signature/finish (fechamento físico do documento).

SAFE-111 · Motor de Validação Server-Side e Descoberta (Verify / Discovery) · 1,0 du

Implementar barramento de consumo para os endpoints de segurança do ecossistema SafeID: /oauth/signature_verify (verificação server-side da validade de hashes assinados), /oauth/certificate-info e /oauth/user-discovery. Retornar DTOs estruturados indicando o status factual (Valid/Invalid) do documento inspecionado.

F4 — Controladores UX, Callbacks Públicos e Homologação Postman (3,0 du)

SAFE-112 · Controller Callback Público, Validação de State e Captura de Negativas · 1,0 du

Criar o Controller público /psc_oauth/callback. Adicionar isenção de guard de login no bootstrap do MY_Controller para esta rota específica. A lógica deve ler o code e state retornados, validar o state contra a sessão gravada no banco, tratar erros amigáveis se receber user_denied e realizar a troca pelo token definitivo chamando o POST /oauth/token no backend.

SAFE-113 · Interface do Portal do Cliente, Estados Visuais e Revogação Ativa · 1,0 du

Desenvolver a interface administrativa em application/views/pages/certificado_psc/. Mapear os estados visuais via jQuery e manipulação de DOM utilizando o DTO do Service: desconectado, conectado, expirado e erro. Incluir ação síncrona acionando o método de revogação local de chaves sem apagar os dados legados do A1. Rota alvo: /certificado_psc no Portal do Cliente.

SAFE-114 · Suíte de Homologação Automatizada Postman (15 Endpoints) · 0,5 du QA

Configurar Coleção Postman parametrizada mapeando as chaves de ambiente para a totalidade dos 15 endpoints previstos no bloco §10. Garantir testes automatizados de asserção de código HTTP (200 OK / 401 Unauthorized) cobrindo caminhos felizes e comportamentos com injeção de dados corrompidos.

SAFE-115 · Auditoria de Segurança de Logs (Grep Scan) & Smoke Test Regressivo A1 · 0,5 du QA

Executar varredura automatizada ou via expressões regulares (grep) nos logs do ambiente de staging para certificar a não exposição de tokens. Realizar teste de fumaça (smoke test) simulando o fluxo de faturamento via eNotas em uma empresa fictícia parametrizada com certificado A1 herdado, gerando evidências de que o barramento PSC opera de forma isolada e sem efeitos colaterais.
