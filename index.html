Definição do Projeto

Conectar o app ContaÁgil (PHP CodeIgniter + jQuery) ao PSC SafeWeb / SafeID, permitindo ao cliente autorizar certificados na nuvem, armazenar tokens com segurança e utilizar a API PSC para assinaturas. O projeto cobre os dois modelos de integração (QRCode e Aplicação Confiável/CA) e os tipos de assinatura previstos (RAW/CMS, ICP, PAdES com carimbo), com validação via Postman restrita ao escopo fechado desta entrega de 15 du.

Funcionalidades do Produto (User Experience)

Conexão e Gestão

  • Multi-fluxo: QRCode (OAuth + PKCE) ou CA (Senha + Identificador).
  • Dashboard de Status: Monitoramento de conexão (Ativo, Expirado, Revogado) via jQuery no portal do cliente.
  • Consultas Integradas: Certificate-info e Discovery direto no app.

Assinatura e Validação

  • Motores PSC: Assinatura de Hash (RAW/CMS) e ICP (AD-RB / AD-RT).
  • Pipeline PAdES: Fluxo completo (Start, Apply, Finish, Info) com suporte a carimbo.
  • Verify: Validação server-side de arquivos/assinaturas via Client Token da aplicação.

Visão do Projeto: Transformação da Assinatura Digital

Alinhamento estratégico: O impacto da transição do modelo de vouchers externos para a integração PSC nativa.

Cenário Atual (Voucher + Soluti)

Fluxo Principal:

  1. Usuário solicita um voucher no ContaÁgil.
  2. Sistema gera código estilo cupom (Ex: QDAS123123ASD).
  3. Usuário leva documentos ao fluxo externo na Soluti.
  4. Informa o voucher na Soluti para validar o serviço/certificado.
  5. Retorna ao ContaÁgil para finalizar o processo.

Dores do Modelo:

  • • Jornada Descontínua: App → Canal Externo → Retorno.
  • • Rastreabilidade: Difícil conciliar eventos Soluti vs Voucher.
  • • Automação Baixa: Validação manual e dependência de A1/A3 locais.
  • • Custo de Suporte: Alto volume para localizar etapa do usuário.

Resultado: Processo lento, dependente de hardware e canais externos, com auditoria limitada.

Com Integração SafeID/PSC (Estado Desejado)

QRCode (OAuth + PKCE)
Autorização via celular gera token de usuário instantâneo. Fim da dependência de drivers e certificados na máquina.

CA (Aplicação Confiável)
Fluxo authorize-ca para uso recorrente pesado. Assinatura fluida e automatizada para o dia a dia.

Ganhos em relação ao Voucher:

  • • Orquestração Nativa: Assinatura disparada e controlled 100% dentro do app.
  • • Pipeline PAdES: Automatização total de carimbos e informações visuais no PDF.
  • • Verify Server-Side: Trava de segurança Valid / Invalid automática em cada documento.
  • • Conformidade: Base ICP-Brasil integrada com trilha de auditoria completa.

"Deixa de ser um código externo e passa a ser assinatura e checagem integradas ao ecossistema ContaÁgil."

§6DDL (guia oficial)

Nota de Validação Técnica: Toda e qualquer coluna abaixo deve ser cruzada com o ambiente real de mysql-dev da ContaÁgil antes de aplicar em staging.

CREATE TABLE IF NOT EXISTS PscOAuthSessions (
  id INT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  state VARCHAR(128) NOT NULL,
  code_challenge VARCHAR(255) NOT NULL,
  code_verifier TEXT NOT NULL,
  CodEmpresa INT NOT NULL,
  CodCliente INT NOT NULL,
  scope VARCHAR(64) NOT NULL DEFAULT 'signature_session',
  redirect_return_url VARCHAR(512) DEFAULT NULL,
  login_hint VARCHAR(20) DEFAULT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  consumed_at TIMESTAMP NULL DEFAULT NULL,
  ip_address VARCHAR(45) DEFAULT NULL,
  user_agent VARCHAR(512) DEFAULT NULL,
  UNIQUE KEY uk_psc_oauth_state (state),
  KEY idx_psc_oauth_created (created_at),
  KEY idx_psc_oauth_empresa (CodEmpresa)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE IF NOT EXISTS PscAccessTokens (
  id INT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  CodEmpresa INT NOT NULL,
  CodCertificado INT DEFAULT NULL,
  scope VARCHAR(64) DEFAULT NULL,
  access_token_enc TEXT NOT NULL,
  expires_at DATETIME NOT NULL,
  authorized_identification_type VARCHAR(8) DEFAULT NULL,
  authorized_identification VARCHAR(20) DEFAULT NULL,
  slot_alias VARCHAR(255) DEFAULT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  revoked_at TIMESTAMP NULL DEFAULT NULL,
  KEY idx_psc_token_empresa (CodEmpresa),
  KEY idx_psc_token_expires (expires_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE IF NOT EXISTS PscApiAudit (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  correlation_id CHAR(36) NOT NULL,
  CodEmpresa INT DEFAULT NULL,
  endpoint VARCHAR(255) NOT NULL,
  http_status SMALLINT DEFAULT NULL,
  duration_ms INT DEFAULT NULL,
  error_code VARCHAR(64) DEFAULT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  KEY idx_psc_audit_corr (correlation_id),
  KEY idx_psc_audit_empresa (CodEmpresa)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

ALTER TABLE Certificados
  ADD COLUMN PscCertificateAlias VARCHAR(255) NULL DEFAULT NULL AFTER Api,
  ADD COLUMN PscAuthorizedDocument VARCHAR(20) NULL DEFAULT NULL AFTER PscCertificateAlias,
  ADD COLUMN PscTokenExpiresAt DATETIME NULL DEFAULT NULL AFTER PscAuthorizedDocument,
  ADD COLUMN PscMetadadosJson TEXT NULL DEFAULT NULL AFTER PscTokenExpiresAt;

§7OAuth + PKCE

  1. Persistir state + verifier + challenge (S256).
  2. Redirect authorize PSC.
  3. Callback: validar state; negar token se user_denied.
  4. POST /oauth/token form; cifrar antes INSERT.

§10Postman

Validação via Postman cobrindo a totalidade dos endpoints previstos no escopo dos 15 du:

  • GET /oauth/authorize (Handshake, PKCE, state)
  • POST /oauth/token (Troca de código por token do usuário)
  • POST /oauth/authorize-ca (Abertura de canal confiável)
  • POST /oauth/pwd_authorize (Handshake de senha da aplicação)
  • POST /oauth/signature (Assinatura digital de hashes RAW/CMS)
  • POST /oauth/signature-icp (Assinatura baseada em políticas)
  • POST /oauth/pades-signature/start (Abertura de fluxo PDF)
  • POST /oauth/pades-signature/apply (Vinculação de carimbo visual)
  • GET /oauth/pades-signature/finish (Encerramento de fluxo PDF)
  • GET /oauth/pades-signature/info (Metadados estruturais do arquivo)
  • GET /oauth/certificate-info (Extração cadastral de chaves)
  • GET /oauth/certificate-discovery (Localização de PEMs públicos)
  • POST /oauth/user-discovery (Elegibilidade do assinante)
  • POST /oauth/client_token (Geração de credencial do app)
  • POST /oauth/signature_verify (Motor validador server-side)

F2 — Barramento HTTP, Integração e Handshakes de Autenticação (5,0 du)

SAFE-104 · Configuração de Ambientes (ENV) & Fail-Fast Boot · 0,5 du

Configurar o isolamento das variáveis do bloco §5 no arquivo env-settings/getenv. Implementar uma validação rígida de boot para que a aplicação lance uma exceção e falhe imediatamente caso constantes essenciais como PSC_TOKEN_ENCRYPTION_KEY estejam ausentes no ambiente de Staging.

SAFE-105 · Wrapper Cliente HTTP PSC & Higienização de Logs · 1,5 du

Criar a classe PscSafeWebClient para centralizar as requisições GET/POST JSON e POST Form x-www-form-urlencoded usando cURL ou Guzzle existente. Mapear retornos HTTP status para exceções específicas do domínio e garantir mascaramento estrito em funções de depuração para nunca imprimir ou vazar tokens em claro nos logs.

SAFE-106 · Camada do Crypto Service (AES-256-GCM) · 0,5 du

Desenvolver métodos no Service para cifragem simétrica de tokens em repouso antes do INSERT na PscAccessTokens. O formato de armazenamento deve ser base64(iv+ciphertext+tag). Adicionar teste de negação lançando exceção controlada se o token gravado for intencionalmente adulterado ou a chave GCM for inválida.

SAFE-107 · Orquestração do Handshake OAuth Inicial com PKCE · 1,5 du

Implementar no Service o método iniciarOAuthPKCE. Gerar code_verifier, code_challenge em S256 e state randômico. Persistir esses hashes temporários na tabela PscOAuthSessions vinculando a empresa e retornar a montagem exata da URL de redirect para o endpoint /oauth/authorize do PSC SafeWeb.

SAFE-108 · Orquestração do Barramento CA (Aplicação Confiável) · 1,0 du

DoR: SAFE-103 e chaves em homolog.

Passos de Execução: Chamar POST /oauth/authorize-ca para receber o identifierCA e metadados. Capturar senha no POST server-side e realizar a concatenação exata password = identifierCA + senhaCertificado para disparar o handshake de recebimento de token via POST /oauth/pwd_authorize.

DoD: Handshake CA operacional e token em repouso guardado de forma idêntica ao fluxo QR.

Implementar o fluxo CA no Service: disparar POST /oauth/authorize-ca para obter o identifierCA (+ state, expirationDate, serialNumber). Guardar o identifierCA e em requisição POST server-side realizar a troca definitiva pelo token de acesso chamando POST /oauth/pwd_authorize passando username e a concatenação exata password = identifierCA + senhaDoCertificado (sem espaços). Persistir token de forma segura.

F3 — Motores Core de Assinatura, Pipelines e Verificação (4,5 du)

SAFE-109 · Motores de Assinatura Core: Hashes Brutos (RAW/CMS) e ICP-Brasil · 1,5 du

Implementar no Service os métodos para disparo de assinaturas digitais por lote de hashes consumindo a API SafeWeb (/oauth/signature) operando em formatos RAW ou CMS. Integrar o motor /oauth/signature-icp suportando as diretrizes normativas das políticas de certificação AD-RB e AD-RT, persistindo as telemetrias em PscApiAudit.

SAFE-110 · Pipeline de Assinatura Documental PDF PAdES & Inspeção de Páginas · 2,0 du

Passos de Execução: Integrar chamadas em lote organizando o fluxo multipasso: /pades-signature/start, /pades-signature/info para resgatar dimensões da página, /pades-signature/apply aplicando carimbo e coordenadas visuais, e /pades-signature/finish para fechamento binário.

DoD: PDF final íntegro, validável, contendo carimbo visual coerente com a inspeção de dimensões do arquivo.

Construir no Service a máquina de estados para o pipeline PAdES: realizar POST /pades-signature/start para obter o documentId, consumir GET /pades-signature/info para capturar as dimensões reais de página e coordenadas do carimbo, acionar POST /pades-signature/apply injetando as annotations e finalizar o fluxo via GET /pades-signature/finish coletando o arquivo assinado.

SAFE-111 · Motor de Validação Server-Side, Discovery e Geração de Chave App · 1,0 du

Passos de Execução: Criar fluxo para consumir POST /oauth/client_token (client_credentials) e cachear em memória. Chamar POST /oauth/signature_verify injetando o Bearer da aplicação para validação fim-a-fim, além dos endpoints complementares `GET /oauth/certificate-info`, `GET /oauth/certificate-discovery` e `POST /oauth/user-discovery`.

DoD: Motor interpretando respostas de integridade de arquivos e chaves usando chaves de servidor de forma isolada.

Implementar lógica no Service para obter e cachear o token corporativo da aplicação via POST /oauth/client_token (grant_type=client_credentials). Integrar a rota validadora POST /oauth/signature_verify assinada com o Bearer da aplicação para capturar status Valid/Invalid de assinaturas, além de implementar o consumo dos endpoints complementares GET /oauth/certificate-info, GET /oauth/certificate-discovery e POST /oauth/user-discovery.
